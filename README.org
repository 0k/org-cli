#+TITLE: org-cli
#+AUTHOR: vaab

* Overview

=org-cli= is a Rust command-line tool for querying and editing org-mode files.

** Goals

- Query org-mode files for information in various helpful ways
- Edit org-mode files safely and compatibly
- Provide machine-friendly output formats for shell integration

** Output Formats

All commands support three output modes:

| Format | Flag | Use Case |
|--------+------+----------|
| Human  | (default) | Interactive terminal use |
| NUL    | =-0= | Reliable bash piping (fixed fields) |
| NDJSON | =-j= / =--json= | Programmatic JSON queries |

* Installation

#+begin_src bash
cargo build --release
#+end_src

* Usage

#+begin_src bash
org-cli --help
#+end_src

** Color control

Human output uses color automatically when stdout is a terminal and respects
the =NO_COLOR= environment variable. Use the global =--color= or =--no-color=
flag to override that behavior; global flags work before or after nested
commands.

#+begin_src bash
org-cli --color syntax check notes.org
org-cli syntax check --no-color notes.org
#+end_src

Using both flags is an error. NDJSON and NUL records remain ANSI-free even
with =--color=.

* Commands

** =headings= — list headings, optionally filtered

List headings from one or more org files. Without filters, prints every
heading; with filters, prints only those that match. When no path is
given, reads the agenda set from
=~/.cache/emacs/org-collect/org-agenda-files.tmp=.

#+begin_src bash
# List every heading (human-readable, with line numbers)
org-cli headings path/to/file.org

# Only headings carrying a :TASK_REF: property (repeatable, AND)
org-cli headings --has-property TASK_REF path/

# Title regex with case-insensitive match
org-cli headings -f "billing" -i path/

# Combine filters (AND); emit NDJSON for downstream tools
org-cli headings -f "billing" -i --has-property TASK_REF -j path/

# Exclude files by glob (repeatable)
org-cli headings --exclude '**/archive/**' path/
#+end_src

NDJSON records carry =file=, =level=, =line=, =keyword=, =done=, =title=,
=tags=, =properties= (full property map), =priority=, =fingerprint=, =etag=,
and =todo_keywords=. NUL records use the fixed-field layout
=level\0line\0file\0keyword\0done\0title\0tags\0priority\0fingerprint\0etag\0todo_keywords\0\0=;
=todo_keywords= is compact JSON. The new NUL fields are appended, so existing
field indices remain stable, but consumers that assert the old exact field
count must be updated.

** =clock check= — is this file's time bookkeeping sound?

The single gate to run after any edit that adds, modifies, or moves a
=CLOCK:= or =FILED:= line. Three rule sets share one exit code (=0=
clean, =1= at least one violation):

1. every closed-range =CLOCK:= line follows the canonical format
   (numerical timezone, consistent precision, matching weekday,
   start ≤ end, accepted zone);
2. every =FILED:= line follows the CLOCK grammar and carries a valid
   customer tag;
3. no two clean =CLOCK:= entries cover the same instant — the one
   *cross-entry* rule.

Rules 1–2 are per-line and scoped to =PATHS=. Rule 3 is pairwise over
=PATHS ∪ agenda set=: a CLOCK just written to one file may collide
with one in *any* other agenda file, and that is exactly what a
post-write check must catch. Only pairs touching =PATHS= are reported;
with no =PATHS= the agenda set is the scope and every pair is. Files
matching =clock.overlap.exclude-globs= (see =clock overlap= below)
contribute no intervals. When the agenda set cannot be read, the sweep
narrows to =PATHS= with a warning on stderr, so a file-local check
keeps working on a machine that never ran org-collect.

#+begin_src bash
# After writing a CLOCK into a project file
org-cli clock check ~/notes/project.org

# Whole agenda set, NDJSON, stop at the first hit
org-cli clock check -j -1

# Narrow both the lint and the sweep
org-cli clock check --exclude '**/archive/**' path/
#+end_src

Human output ends with one summary line per rule set — =All CLOCK
lines OK.=, =All FILED lines OK.=, =No overlapping CLOCK entries.= —
or the matching red count, so a green run reads as three distinct
facts and a red one names which rule set failed.

Records are anchored on one line. NDJSON fields are =file=, =line=,
=tag=, =message=, =raw=; an =overlap= record additionally carries
=other= (=file=, =line=, =raw= of the other side) and
=overlap_seconds=, anchored on the earlier-starting line — or on the
line inside =PATHS= when only one side is. NUL records are
=file\0line\0tag\0message\0raw\0\0=; an =overlap= record appends
=other-file\0other-line\0other-raw\0= before the terminator so
existing field indices stay stable.

** =clock list= — list CLOCK lines, optionally filtered by parent heading

In its default form, =clock list= is a flat scanner emitting every
valid CLOCK line. When any heading filter is set (=--has-property=,
=-f= / =--filter=, =-i= / =--ignore-case=), traversal becomes
heading-aware: only CLOCKs whose enclosing heading matches are kept,
and each emitted NDJSON record gains a =heading= field with the
parent's =level=, =line=, =title=, =tags=, =properties=.

#+begin_src bash
# Every CLOCK line (unchanged behavior)
org-cli clock list path/

# Only CLOCKs under :TASK_REF: headings (with parent heading embedded)
org-cli clock list --has-property TASK_REF -j path/

# Only CLOCKs under headings whose title matches "billing" (case-insensitive)
org-cli clock list -f "billing" -i -j path/

# Combine filters (AND)
org-cli clock list -f "billing" -i --has-property TASK_REF -j path/
#+end_src

With no heading filter, NDJSON output is byte-identical to the
pre-filter shape — existing consumers are unaffected.

** =clock list-filed= — declared customer time

A =FILED:= line records a time segment that was declared to a
customer's accounting system and is frozen there. It uses exactly the
closed-range CLOCK grammar plus a mandatory customer tag:

#+begin_example
FILED: [2026-08-24 Mon 10:00 +0200]--[2026-08-24 Mon 11:00 +0200] =>  1:00  # lok
#+end_example

Customer tags match =[a-z0-9][a-z0-9_-]*=. FILED segments are not work
time: =clock list=, =clock check=, =clock overlap=, and =clock fix=
ignore them, so they are never counted, summed, checked for overlap, or
rewritten. A distinct five-letter keyword keeps the line aligned with
=CLOCK:= while remaining ordinary paragraph text to Emacs; consequently
=org-clock-sum=, =org-find-open-clocks=, and org-element clock parsing
also ignore it.

#+begin_src bash
# List every valid FILED line in human-readable form
org-cli clock list-filed path/

# Emit NDJSON for one customer
org-cli clock list-filed --customer lok -j path/

# Emit fixed-field NUL records
org-cli clock list-filed -0 path/

# Validate FILED grammar and customer tags (the FILED pass of check)
org-cli clock check path/
#+end_src

The =list-filed -j= fields are =file=, =line=, =start=, =end=, and
=tag=. Machine =start= and =end= values are UTC integer seconds since
the Unix epoch. NUL records use the same order, with NUL between fields
and a double-NUL record terminator. Invalid FILED lines are diagnosed
and excluded from listing; =list-filed= exits 1 when it finds one, and
=clock check= reports them alongside its CLOCK and overlap findings.

** =clock overlap= — find CLOCK lines covering the same instant

The one cross-entry rule: it compares each clean CLOCK entry against
every other one across the whole corpus, because you cannot be doing
two things at the same time. =clock check= runs the same rule as its
third pass; =clock overlap= is the pair-oriented, sortable view of it
for auditing a corpus.

Intervals are *half-open* =[start, end)=: =10:00–11:00= and
=11:00–12:00= are adjacent, not overlapping — that is exactly the
shape clocking out of one task and into the next produces. A
zero-length =⇒ 0:00= clock spans no instant and never conflicts.
Comparison uses true instants, so =09:30 +0800= and =09:30 +0200= are
correctly seen as six hours apart.

#+begin_src bash
# Whole agenda set (exit 1 if any overlap is found)
org-cli clock overlap

# A subtree, as NDJSON
org-cli clock overlap -j path/

# Stop at the first conflicting pair
org-cli clock overlap -1 path/

# Shortest shared span first; for ties, latest shared start first
org-cli clock overlap --sort duration --sort start:desc path/
#+end_src

=--sort FIELD[:asc|desc]= orders results by the shared overlap span.
Fields are =start= (the later CLOCK start), =end= (the earlier CLOCK
end), and =duration= (the shared seconds); direction defaults to
=asc=. The option is repeatable, with earlier keys taking precedence.
Sorting is stable, so records tied on every requested key retain their
detector order. Without =--sort=, detector order is unchanged.
=--first= is applied after sorting, and human, NUL, and NDJSON output
all use the same resulting order.

Lines that fail the per-line rules are skipped with a warning rather
than aborting the run: a line whose own timestamps are broken cannot
be placed on a timeline, but the rest still can. =clock check= reports
those lines itself, so it stays silent about skipping them.

*** Declaring which CLOCK lines are work logs

Not every CLOCK line records time spent working. Files matching
=clock.overlap.exclude-globs= contribute no intervals:

#+begin_src yaml
clock:
  overlap:
    exclude-globs:
      - ~/notes/activity/**    # activity segments
      - ~/notes/presence/**   # presence windows
#+end_src

The two classes above are *evidence*, not work logs: segment files are
the raw material a work log is written from, and a presence window is
one CLOCK per stay in a place — routinely months long, so it overlaps
essentially every work clock by construction.

A leading =~/= is expanded to the home directory. The =--exclude= flag
adds to this list rather than replacing it.

NDJSON records carry =a= and =b= (each with =file=, =line=, =start=,
=end=, =raw=) plus =overlap_seconds=; =a= is always the
earlier-starting side. NUL records use
=a_file\0a_line\0b_file\0b_line\0seconds\0a_raw\0b_raw\0\0=.

** =heading= — edit headings (set / add / delete / move)

Edit org-mode headings in place. A target heading is addressed either
by a =/=-separated title path (=A/B/C=; write =\/= for a literal slash
in a title) or by =--line N=. Every command is a *dry-run by default*,
printing a unified diff; pass =--write= to apply the change atomically
(temp file + rename in the same directory). =-j= emits one NDJSON
=EditRecord= per applied op (with =file= and =dry_run= fields), =-0=
NUL-separated =file\0op\0line\0\0= records. The rest of the file stays
byte-for-byte untouched.

#+begin_src bash
# Set fields (applied in order: keyword, title, tags, properties, content)
org-cli heading set file.org "Parent/Child" --keyword TODO --title "New title" --write
org-cli heading set file.org --line 12 --add-tag urgent --remove-tag draft --write
org-cli heading set file.org --line 12 --set-tags "a,b"        # "" removes all tags
org-cli heading set file.org "Task" --property TASK_REF=248 --write
org-cli heading set file.org "Task" --content - --write < body.txt   # or --content-file F

# Add a heading under a parent at a position (first|last|before=N|after=N)
org-cli heading add file.org --under "Parent" --position last --title "New child" --write
org-cli heading add file.org --keyword TODO --title "Top level" --tag x --tag y --write

# Delete a subtree
org-cli heading delete file.org "Parent/Child" --write

# Move a subtree within a file, or to another file (re-leveled to depth)
org-cli heading move file.org "A/B" --under "A" --position after=2 --write
org-cli heading move file.org "Moving" --to-file other.org --under "Dest" --write
#+end_src

The keyword set honours an in-buffer =#+TODO:= declaration (falling
back to =TODO=/=DONE=); =--keyword= must name a keyword from that set.
For =move=, positions are relative to the destination *after* the
source subtree is removed. Cross-file moves write the destination
first, then the source, so a crash between the two writes duplicates
the subtree rather than losing it.

** =link move= — relocate paths without breaking file links

Move one file or directory inside an explicitly scanned root while
preserving every supported =[[file:...]]= edge in that corpus. The
command scans all =.org= files recursively with the same all-followable
semantics as =link check=, including links in body text, drawers, and
property values.

The default is a read-only dry-run with a deterministic summary and
unified diffs. =--write= moves the filesystem object, atomically writes
each changed org file, and then verifies the resulting link graph. A
write requires the corpus and its path tree to remain *quiescent*: no
non-cooperating process may mutate relevant files or paths until the
command returns.

#+begin_src bash
# Preview a file relocation and every affected link target
org-cli link move notes/old.org notes/new.org --root notes

# Move a directory and apply all inbound/outbound link rewrites
org-cli link move archive/old archive/renamed --root . --write

# Preview/apply one simultaneous strict YAML batch
org-cli link move --plan renames.yaml --root .
org-cli link move --plan renames.yaml --root . --write
#+end_src

The two input modes are mutually exclusive: provide exactly positional
=OLD NEW= or =--plan YAML=. Batch plans use this strict dash-cased schema
(unknown keys are errors):

#+begin_src yaml
moves:
  - from: visits/old
    to: visits/new
#+end_src

Relative =from=/=to= paths are resolved from canonical =ROOT=, not the
shell's working directory. Absolute paths are accepted only inside
=ROOT=. Batch mappings are simultaneous: every source and link is
resolved in the initial tree and mapped at most once into the final
tree. Preview and execution list moves in YAML order; rewritten files
are diffed in final-path order.

=OLD= must exist; =NEW= must not exist; both paths must be inside
=ROOT=; and =NEW='s parent must already exist. Relative links remain
relative to each source file's post-move directory, absolute links
remain absolute, and descriptions and =::= anchors are not rewritten.
Batch mode additionally refuses empty/duplicate/overlapping sources or
destinations, occupied destinations, destinations inside sources, and
all FROM/TO cross-collisions (including chains, swaps, and cycles).
All moves and rewrites form one ordinary-I/O transaction: move failure,
write failure, or postflight failure restores rewritten files and then
rolls applied destinations back in reverse move order when freshness
checks permit.

On an ordinary I/O or post-write verification failure, the command
attempts to restore every rewritten file and move =NEW= back to =OLD=.
On Linux, one nonblocking exclusive =flock= on the canonical =ROOT=
directory serializes cooperating =org-cli link move= writers without a
persistent lock file across planning, execution, and postflight. Writers
serialize only when they use the same canonical =ROOT=; nested or
overlapping different root values are outside cooperative serialization.
Both filesystem moves use atomic no-replace semantics.
=--write= fails safely as unsupported on other platforms. Freshness
checks reject stale bytes and path entries that have become symlinks;
rollback likewise refuses a stale or substituted entry and reports
incomplete restoration instead. These are cooperative serialization
and boundary detection, not protection against an uncooperative actor
changing a path between system calls.
This rollback is tested, but it is not crash recovery: the operation
does not yet have a durable journal, so process termination or power
loss can still require manual recovery.
